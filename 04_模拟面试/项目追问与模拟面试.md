# 项目追问与模拟面试

目标：把项目讲成“真实做过、能解释取舍、能接受追问”的样子，而不是背八股。

---

## 1. 项目介绍模板

### 60 秒版本

1. 项目是什么：一句话说明业务或技术目标。
2. 你负责什么：明确模块，不要说成全是自己做的。
3. 技术架构：主流程、核心组件、数据流。
4. 难点：并发、性能、可靠性、数据一致性中选一个。
5. 结果：指标、功能完成度、压测结果、踩坑修复。

示例结构：

```text
这个项目是一个基于 Linux 的 C++ HTTP 服务端，目标是支持高并发短连接请求。
我主要负责网络 IO、线程池、定时器和日志模块。
整体采用 Reactor 模型，主线程 epoll 监听连接事件，工作线程处理请求解析和业务逻辑。
比较难的是连接生命周期和并发关闭，最初在压力测试中出现过 fd 复用导致的错误写回。
后来我用 RAII 封装 fd，统一连接状态机，并在关闭路径上做了幂等处理。
压测时在本机固定参数下 QPS 从 X 提升到 Y，P99 从 A 降到 B。
```

## 2. WebServer 项目追问链

### 第一层：架构

**面试官问：为什么用 epoll？**

回答：连接数较多但同一时刻活跃连接相对少，epoll 不需要每次线性扫描全部 fd，适合这类 IO 多路复用场景。它把关注 fd 集合维护在内核，用户态每次拿到的是就绪事件列表。

**面试官问：LT 和 ET 你怎么选？**

回答：如果强调实现稳定，先选 LT，逻辑简单，不容易漏事件。如果追求更少事件通知和更高性能，可以用 ET，但 fd 必须非阻塞，并且读写循环直到 `EAGAIN`，否则缓冲区剩余数据可能不再触发通知。

**面试官问：一个请求的完整流程？**

回答：accept 新连接，设置非阻塞，注册到 epoll；可读事件触发后读取到连接读缓冲；解析 HTTP 请求行、头部和 body；生成响应；如果一次写不完，把剩余数据放写缓冲并关注可写事件；写完后根据 keep-alive 决定保留或关闭连接。

### 第二层：并发

**面试官问：IO 线程和工作线程怎么分工？**

回答：IO 线程负责事件监听和非阻塞读写，避免被业务阻塞。CPU 或业务处理任务投递到线程池。工作线程完成后把响应交回连接对象，再由 IO 线程负责写回。这里要注意连接对象生命周期，不能让工作线程持有已经关闭的连接裸指针。

**面试官问：线程池队列满了怎么办？**

回答：要有背压策略。可以阻塞提交者、直接拒绝并返回错误、丢弃低优先级任务、扩容线程或队列。服务端更常用的是限流/拒绝，避免无限排队把延迟拖崩。

**面试官问：怎么保证连接对象不会被提前释放？**

回答：常见做法是用状态机和引用计数/智能指针管理。IO 线程关闭连接时只标记状态，等没有任务引用时再释放。回调中使用 `weak_ptr` 升级，失败说明连接已关闭，直接放弃写回。

### 第三层：性能

**面试官问：怎么压测？**

回答：先固定机器、线程数、连接数、请求大小、keep-alive 策略和系统参数，再用 wrk/ab 等工具压测。关注 QPS、平均延迟、P95/P99、CPU、内存、上下文切换、网卡、fd 数。每次只改一个变量，避免结果不可解释。

**面试官问：瓶颈怎么定位？**

回答：CPU 高用 perf/火焰图看热点；系统调用多用 strace；锁竞争看 perf lock 或日志采样；内存增长看 ASan/Valgrind/heap profiler；IO 等待看 iostat、ss、netstat；业务慢看分阶段耗时日志。

## 3. 线程池项目追问链

**问：线程数怎么定？**

回答：CPU 密集型接近 CPU 核数或核数加少量；IO 密集型可以更多，但要结合阻塞比例、上下文切换和下游承载能力。工程上一般通过压测找最优点，而不是固定公式。

**问：任务抛异常怎么办？**

回答：worker 循环里要捕获异常，记录日志，避免线程直接退出。如果使用 `packaged_task`，异常可以传递到 future；如果是 fire-and-forget 任务，也至少要隔离异常并保证 worker 继续服务。

**问：析构时队列里还有任务怎么办？**

回答：要定义清楚语义。优雅关闭是停止接收新任务，执行完队列剩余任务再退出；快速关闭是清空队列并让 worker 退出。两者都要唤醒所有等待线程并 join。

## 4. 缓存项目追问链

**问：为什么引入缓存？**

回答：缓存不是为了显得高级，而是为了解决读多写少、重复查询、下游数据库压力和响应延迟问题。要说明命中率、过期策略、数据一致性要求和降级方案。

**问：缓存和数据库怎么保持一致？**

回答：常见策略是更新数据库后删除缓存，而不是直接更新缓存。读请求缓存未命中时回源数据库并回填。并发场景要考虑删除失败重试、延迟双删、消息队列异步删除或订阅 binlog。强一致要求高的场景不应只靠普通缓存。

**问：热点 key 怎么处理？**

回答：可用本地缓存、多级缓存、逻辑过期、互斥重建、热点预热、请求合并。核心是避免热点 key 过期瞬间所有请求打到数据库。

## 5. MySQL 项目追问链

**问：慢 SQL 怎么优化？**

回答：先用慢查询日志和 `EXPLAIN` 看执行计划，确认访问类型、扫描行数、是否使用索引、是否回表、是否 filesort/temporary。优化方式包括合适联合索引、覆盖索引、改写条件避免函数/隐式转换、分页优化、减少返回列、拆分大事务。

**问：索引是不是越多越好？**

回答：不是。索引会占空间，写入时要维护索引，过多索引会降低 insert/update/delete 性能，也可能让优化器选择复杂。索引要围绕高频查询、过滤性、排序和覆盖需求设计。

## 6. 45 分钟真人感模拟面试脚本

### 时间分配

| 时间 | 模块 | 目标 |
|---|---|---|
| 0-5 分钟 | 自我介绍 + 项目概览 | 看表达和项目边界 |
| 5-15 分钟 | 项目深挖 | 只追一个核心难点，不无限扩展 |

| 25-33 分钟 | OS/网络 | epoll、TCP、线程同步 |

```text
你现在扮演 C++ 后端一面面试官。

1. 总时长 45 分钟，按项目、C++、OS/网络、数据库/缓存、手撕代码分配时间。
```

## 8. 高频项目风险点

- 简历写“高并发”，但没有压测指标。
- 写“线程池”，但说不清停止策略和任务队列。
- 写“epoll”，但不知道 LT/ET 和非阻塞读到 `EAGAIN`。
- 写“缓存”，但说不清穿透、击穿、雪崩和一致性。
- 写“优化”，但没有定位工具和前后指标。
- 写“分布式”，但所有细节都是单机实现。
- 写“熟悉 C++11”，但移动语义、智能指针、lambda 只能背名词。
